# Doubt journal

An academic journal with one reviewer. Every paper I read gets a folder, a public review, a
rating, and — if I bothered to rebuild it — the notebooks I wrote to understand it.

It is also a game. Reading carelessly scores 1; rebuilding a paper from scratch scores 8. The
scoreboard is computed from the reviews themselves, so the only way to move a number is to
actually read something.

- **Papers** — <https://act65.github.io/doubt-journal/papers/>
- **Scoreboard** — <https://act65.github.io/doubt-journal/stats/>

## Layout

```
_papers/<slug>/index.md     the minimal review — tldr, then the rubric axes with their reasons
_papers/<slug>/tutorial.md  optional longer pages: tutorial, discussion, thoughts (+ private notes.md)
_papers/<slug>/*.py         marimo notebooks that rebuild the idea in JAX
_data/rubric.yml            the rubric — the axes every review is scored on; rendered at /rubric/
_data/parts.yml             the optional pages beside a review, in reading order
_data/tags.yml              tag vocabulary: label + kind (topic / archetype / meta)
_data/queue.yml             the papers waiting to be read — NOT published; what gets sampled
_data/dropped.yml           papers that left the queue unread, so an import can't bring them back
_data/sampling.yml          how the draw is biased: recency halflife, strike cost, per-tag interest
_data/gamify.yml            the rules: XP per depth, ranks, annual target, review deadline
_data/stats.yml             GENERATED by scripts/score.py — committed so XP shows up in the diff
tags/<slug>.md              GENERATED stub pages, one per tag in use
_posts/                     the older reviews, from before papers had folders
```

There are no nested folders. Grouping is done with **tags**, so a paper can sit under
`probabilistic-methods` and `hidden-equivalence` at once, and `/papers/` filters on any
combination of them.

## Picking what to read next

Choosing is the part I'm worst at, so I don't. `_data/queue.yml` holds a few thousand papers —
my whole Zotero library, the reading lists that accumulated in Google Keep, years of Google
Scholar alerts, and the folders in here I started and never finished — and one gets drawn:

```sh
python scripts/next_paper.py                 # draw one and decide
python scripts/next_paper.py --tag rl        # draw from one tag only
python scripts/next_paper.py --explain       # show how the weight was built
python scripts/next_paper.py --top 20        # the heaviest entries, no draw
python scripts/next_paper.py --due           # what I've accepted, and when it's due
```

```
drawn from 2488 papers (1.69% chance, 1st heaviest)

  Inference via Interpolation: Contrastive Representations Provably Enable Planning
  Eysenbach, Myers, Salakhutdinov & Levine · 2024 · papers · curated
  https://arxiv.org/abs/2403.04082
  tags: rl, probabilistic-methods, hidden-equivalence
  half-written already: _papers/inference-via-interpolation/ (published, not finished)

  [r] review it   start the clock, 14 days to finish the review
  [s] skip        strike 1 of 2
  [d] drop        remove it from the queue now
  [q] quit        change nothing
```

It's a weighted draw, not a shuffle. Recent interests come up more often — the weights are in
`_data/sampling.yml` — but every paper keeps a real chance, so something I wrote down in 2018
and forgot can still surface. **Skipping costs a strike**, and the second strike removes the
paper for good; a tombstone goes in `_data/dropped.yml` so the next import can't hand it back.

Accepting one starts a clock. The review is due in two weeks, and after that every finished
week costs XP until the review is finished — capped per paper, so one abandoned draft
can't zero the scoreboard. CI rescores daily, so the deadline bites without a push.

### Building the queue

```sh
python scripts/import_queue.py --bib ~/all-zotero.bib --keep ~/keep-dump.md \
    --mbox ~/scholar.mbox
python scripts/import_queue.py          # re-sync _papers/, keep everything else
python scripts/resolve_queue.py         # the one networked script: look up missing titles/links
python scripts/resolve_queue.py --pmlr v97    # ...against a PMLR volume index instead
```

`--mbox` takes a Gmail Takeout export of Google Scholar alerts. Label the alerts in Gmail
(`from:scholaralerts-noreply@google.com`), Takeout that one label as `.mbox`, and every
message arrives carrying an `X-Gmail-Labels:` header — so a star survives the trip without
exporting your starred mail separately. Anything you put in the bin stays out: your deletions
are the first filter the queue gets.

Scholar is the biggest source by a long way — about 12k paper mentions from 9.8k alerts — and
the weakest per paper, since most are "a new paper by someone I follow" rather than a topic
I searched for. `source_interest` in `_data/sampling.yml` damps a source that floods the
draw; it ships neutral.

A star is the strongest signal in the queue, but it lands on an *email*, which may hold
several papers. So it is divided by how many: a starred alert with one paper in it is
unambiguous and that paper is simply `starred`, while an alert with k papers marks all k
`flagged` with `siblings: k` and splits the boost `1 + (starred - 1) / k` between them.
`next_paper.py --flagged` draws that shortlist, so you can promote the right one yourself.

Patents, conference abstracts and blog mirrors are dropped on the way in — a patent isn't a
paper you can review. Anything you've already curated, starred or accepted is never filtered
out by that rule.

Neither Zotero nor Keep records when something was added, so `added` is an estimate there —
Zotero's access date, or the arXiv month in a link read against Keep's newest-first ordering —
and `added_est: true` marks the guess. Scholar alerts have a real `Date:` header, so they're
the one source dated exactly. Re-importing is safe: strikes, deadlines and looked-up titles
survive.

## Adding a paper by hand

```sh
python scripts/new_paper.py bfn --title "Bayesian Flow Networks" \
    --ref https://arxiv.org/abs/2308.07037 --authors "Graves et al." --year 2023 \
    --depth read --tags probabilistic-methods,generative-models

# or pull the metadata out of the queue:
python scripts/new_paper.py neural-collapse --from-queue "neural collapse"
```

Then score and answer each axis of the rubric, and rescore.
Add a longer page when you need one:

```sh
python scripts/new_paper.py bfn --part tutorial      # or discussion, thoughts
```

and rescore:

```sh
python scripts/score.py
```

Which prints the damage:

```
  2 papers · 16 XP · Desk Clerk
  9 XP to Reviewer 2 (64%)
  2/52 in 2026 (27.6 behind pace)
  streak 1 week (best 1)
```

Commit `_data/stats.yml` along with the review — the diff is the scoreboard's history.

## How a review is laid out

A paper's page is the minimal review, read top to bottom; the longer writing is linked from it.

| where | | |
|---|---|---|
| `tldr` | required | The whole paper in a sentence or two. |
| `review.why` | required | The problem — real, hard, worth solving? |
| `review.idea` | required | The solution — principled and well motivated, or ad hoc? |
| `review.contribution` | required | The delta — what it adds that wasn't known or possible before. |
| `review.rigour` | required | A claims table: claim · evidence · holds? (yes / partly / no / unverified) |
| `review.scope` | required | An assumptions table: assumption · stated? · implications. |
| `review.clarity` | required | One simple narrative — a motivated problem, minimal experiments, an easily interpretable result? |
| `confidence` | optional | How sure (1–5). Not part of the rating. |
| `takeaways` | optional | One or two things worth remembering. |
| body of `index.md` | optional | A short verdict paragraph. |
| `tutorial.md` → `/tutorial/` | optional | The extended summary — the tutorial I wish I'd been handed. |
| `discussion.md` → `/discussion/` | optional | The long argument behind the verdict, and feedback for the authors. |
| `thoughts.md` → `/thoughts/` | optional | My ideas, extensions, and open questions. |

Each axis is scored 1–4 and carries its reasons — an answer (or the table), plus `plus` and
`minus` points. The axes and their questions live in `_data/rubric.yml`; edit them there. Write
it in the other order: the axes while reading, the tldr and takeaways last. A review isn't
finished — and gets no verdict — until every axis is scored and answered and there is at least
one plus and one minus. `scripts/score.py` lists what each one still lacks.

## Scoring

`depth` is the honest bit. It records how hard you actually looked, not how long the review is.

| depth | XP | means |
|---|---|---|
| `read` | 1 | read it properly, could summarise the argument |
| `rebuilt` | 3 | reimplemented the core idea; there is a notebook |
| `extended` | 5 | went past the paper — a new experiment, a case it gets wrong |

One read is the unit. There is no credit for skimming — if you only got as far as the abstract
and the figures, it doesn't go in the journal.

The rating is never written by hand. It is the mean of the axis scores rescaled to 0–10, and a
1 on any axis caps it at 4, so one fatal flaw can't be outvoted by the rest. At or above 5 the
paper is **accepted**, below it **rejected**, and a review that isn't finished is **under
review** whatever its scores. Unfinished is not zero — a paper you haven't judged yet is
different from one you thought was worthless.

Ranks run Desk Clerk → Reviewer 2 → Reviewer → Area Chair → Senior AC → Program Chair →
Editor-in-Chief. Badges, streaks, the idle-week penalty and the two-week review deadline are
all configured in `_data/gamify.yml`; edit the thresholds there rather than in the script.

## Notebooks

```sh
uv run marimo edit _papers/bfn/bfn_simple.py     # interactive
uv run marimo run  _papers/bfn/bfn_simple.py     # read-only app view
```

`uv` resolves the environment from `pyproject.toml` / `uv.lock` on first run. The notebooks pin
`JAX_PLATFORMS=cpu` and enable float64 themselves, so they run anywhere. They are linked from
each paper page but not served by the site — GitHub renders them fine.

## Building the site

```sh
bundle install
bundle exec jekyll serve
```

Pushes to `master` build and deploy through `.github/workflows/pages.yml`. The workflow reruns
`score.py` before building, so the site is always scored as of the build date (UTC), and a
daily cron rebuild makes idle-week XP losses and missed review deadlines land without a push.
It cannot use the stock GitHub Pages build because the site uses `jekyll-scholar` and a
`_plugins/` file, both of which that build ignores.

## Conventions

- **One folder per paper**, slug short and lowercase (`bfn`, `enn`) — it's what you type to open
  the notebook.
- **Notebooks are marimo `.py` files**, not `.ipynb` — they diff cleanly in git.
- **Notebook names describe the angle**, not the paper: `epistemic_nn_from_coins.py` and
  `epistemic_nn_from_gaussian.py` are two routes to the same idea. Several small notebooks
  attacking one paper from different directions beats one big one.
- **Build up, don't summarize.** Start from something already understood (a coin, a Gaussian)
  and climb to the paper's construction.
- **PDFs are gitignored.** Link to the paper in the front matter `ref:` instead.
